# Предметная модель первой версии

Статус: согласовано с владельцем после ревью 4 ноября 2026 года.
Границы модулей и связи уточнены с владельцем 12 ноября 2026 года.
Правила продукта берутся из [согласованной первой версии](first-version.md); модель определяет распределение ответственности.
Термины определены в [DOMAIN.md](../DOMAIN.md).

## Назначение и границы

Модель связывает понятия первой версии с владельцами данных и сквозными сценариями.
Модуль здесь означает область ответственности приложения, а не отдельный процесс развёртывания.
Стек, протокол и схема хранения остаются решениями реализации.

Основание решений — [исследование учебного проекта](research/ai-first-platform-issue-1-pr-7-pr-9.md).
Его сокращённая поставка не переносится: интеграция GitHub и проверенный отзыв остаются обязательными.

## Связи согласованных понятий

- Сотрудник может получать назначения доступа к нескольким проектам.
- Проект объединяет репозитории и один редактируемый документ инструкций.
- Репозиторий может входить в несколько проектов; участие в одном не открывает инструкции остальных.
- Назначение доступа задаёт разрешение на проект, но не доказывает фактическую выдачу прав в GitHub.
- Внешнее назначение может сохранять фактический доступ независимо от назначений платформы.
- Агент получает содержимое в пределах текущих прав сотрудника; собственных назначений проектов у агента нет.

Правила административного доступа, приватности репозиториев и готовности окружения определены в соответствующих сценариях первой версии.

## Модули

Выделены пять модулей с одним владельцем каждого вида данных.
Обоснование выбора владельца разрешений находится в [ADR-0001](adr/0001-platform-access-ownership.md).

| Модуль | Владеет | Предметный интерфейс |
| --- | --- | --- |
| Сотрудники | Приглашения, учётные записи, подтверждение личности, активность сотрудника | Пригласить; принять приглашение; войти; определить активность; заблокировать сотрудника |
| Проекты | Состав проектов, связи с репозиториями, документ инструкций | Создать проект; изменить репозитории; изменить инструкции; предоставить разрешённое содержимое |
| Доступ | Назначения проектов, административные полномочия, правила разрешений; состояние сквозных операций выдачи и отзыва | Назначить доступ; исключить участника; проверить разрешение; начать и повторить операцию; показать результат |
| Подключения агентов | Принадлежность и действительность подключения | Определить сотрудника; проверить подключение; отозвать подключение |
| Интеграции | Подтверждённая связь с GitHub, результаты внешних операций и проверок | Подтвердить GitHub-аккаунт; выдать права; отозвать назначение; проверить фактический доступ; сообщить препятствия |

Каждый модуль изменяет только собственные данные; координация сценария не передаёт координатору владение чужими данными.
«Доступ» получает активность сотрудника и действительность подключения у владельцев этих данных.
«Интеграции» сообщает внешние факты; правила участия в проекте определяет «Доступ».

## Сквозные сценарии

Распределение ответственности ниже не задаёт обязательный порядок технических вызовов.
Критерии завершения и исключения заданы в [обязательных сценариях v1](first-version.md#обязательные-сценарии).

### Приглашение и чтение

| Сценарий | Распределение ответственности |
| --- | --- |
| Приглашение и вход | «Сотрудники» подтверждает приглашение и личность; «Интеграции» подтверждает принадлежность GitHub-аккаунта до выдачи прав |
| Чтение сотрудником | «Доступ» учитывает активность и назначения; «Проекты» предоставляет разрешённое содержимое |
| Чтение агентом | «Подключения агентов» определяет владельца и действительность; затем применяются проверки доступа сотрудника |

### Назначение проекта

«Доступ» проверяет полномочия администратора и создаёт назначение; «Проекты» сообщает репозитории; «Интеграции» выдаёт права.
Действующее назначение открывает активному сотруднику инструкции проекта, даже если права в GitHub выданы не полностью.
«Доступ» отдельно показывает незавершённую выдачу прав.

### Изменение состава проекта

«Проекты» сохраняет новый состав независимо от доступности GitHub.
«Доступ» организует изменение прав участников через «Интеграции» и ведёт незавершённую операцию при сбое.

### Выдача и отзыв доступа

«Доступ» ведёт состояние выдачи и отзыва, включая повторные попытки и итог для администратора.
«Интеграции» выполняет внешние действия и возвращает результат; решение о завершении принимает «Доступ».

Операция хранит область изменения и незавершённые действия; точный формат состояния оставлен реализации.
Частичный результат, ошибка действия и невозможность проверки должны оставаться различимыми для администратора.

При исключении участника «Доступ» прекращает назначение и рассчитывает оставшиеся основания, включая другие проекты с общим репозиторием.
«Интеграции» отзывает ненужные назначения платформы; повторное выполнение также учитывает текущие назначения.

«Доступ» сохраняет перечень проверяемых репозиториев незавершённого отзыва, даже если их затем исключили из проекта.
Он завершает отзыв только после проверки результата в сохранённой области.
«Проекты» хранит текущий состав, а состояние незавершённых операций доступа хранит «Доступ».

«Интеграции» проверяет фактический доступ и возвращает препятствия; «Доступ» сохраняет незавершённую операцию либо подтверждает результат.
После ручного устранения внешнего назначения «Интеграции» повторно проверяет доступ.

### Уход сотрудника

Команду ухода сотрудника принимает «Доступ»: проверяет полномочия администратора, сохраняет операцию и координирует её выполнение.
«Сотрудники» блокирует учётную запись; «Подключения агентов» отзывает подключения; «Интеграции» выполняет внешний отзыв и проверки.
Интерфейс администратора отправляет одну команду этому координатору.

Блокировка сразу прекращает выдачу новых данных сотруднику и его агентам, независимо от отзыва подключений и доступности GitHub.
Сотрудник остаётся заблокированным при незавершённом внешнем отзыве.

## Подключение агента

Подключение учитывается отдельно от клиента, запуска и разговора агента.
Подключение принадлежит одному сотруднику и может быть отозвано без изменения назначений этого сотрудника.
«Доступ» проверяет текущие права владельца при обращении агента.

В первой версии поддерживается один выбранный вид агента.
«Доступ» разрешает агенту только получение доступных сотруднику проектов, репозиториев и инструкций, включая случай сотрудника-администратора.
Административные действия агенту недоступны.

Локальный агент выполняет подготовку окружения и проверочную команду, затем сообщает сотруднику результат.
Платформа не ведёт отдельный процесс подготовки и не хранит статус готовности окружения.
Критерий готовности определён в [сценарии подготовки окружения](first-version.md#5-работа-агента-и-подготовка-окружения).

## Открытые решения

Следующие правила учебного проекта не переносятся автоматически:

- Одноразовость, отмена и сроки приглашения, поведение повторного приглашения.
- Намеченные проекты внутри приглашения и момент создания учётной записи.
- Количество подключений, создание подключения и полномочия на отзыв чужого подключения.
- Возвращение сотрудника и возможность восстановления прежних назначений.
- Защита последнего администратора и её совместимость с обязательным отзывом при уходе.
- Закрытие проекта, удаление последнего репозитория и удаление инструкций.

Перед реализацией остаётся определить технические гарантии отзыва для начатых запросов и изменение прав во время внешней операции.
При выборе способа проверки всех оснований GitHub-доступа применяются [критерии приёмки v1](first-version.md#критерии-приёмки).
Первоначальная настройка, клиент, протокол и остальные технические решения перечислены в [v1](first-version.md#решения-команды-перед-реализацией).

Открытые решения не считаются согласованными вследствие принятия этой модели.
