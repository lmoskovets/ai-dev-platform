Этот документ фиксирует согласованный объём; задачи реализации ведутся в GitHub Issues.

## Цель и критерий готовности

Первая версия помогает подключить сотрудника и его агента к проекту, подготовить рабочее окружение и затем отозвать доступы.
Она обслуживает одну компанию и одну организацию GitHub.

Версию принимают после проверки полного цикла на настоящем проекте:

1. Сотрудник принимает приглашение и подтверждает принадлежность аккаунта GitHub.
2. Администратор назначает сотруднику доступ к проекту.
3. Сотрудник получает доступ ко всем репозиториям и инструкциям проекта.
4. Сотрудник подключает поддерживаемого агента разработчика.
5. Агент готовит окружение и успешно выполняет проверочную команду из инструкций.
6. Администратор инициирует отзыв при уходе сотрудника.
7. Платформа блокирует сотрудника и его агента, отзывает доступы в GitHub и проверяет результат.

Скачанные репозитории без успешной проверки окружения не означают завершённое подключение.
Отмена собственных назначений без проверки фактического доступа не означает завершённый отзыв.

## Выбранная граница

Согласован полный цикл подключения и отзыва доступа, включая реальные операции в GitHub.
Каталог проектов без управления доступами не выполняет начальные требования заказчика.
Расширение на другие этапы разработки откладывается до получения опыта первой версии.

Цена выбранной границы — необходимость обрабатывать частичные результаты и внешние назначения уже в первой версии.
Допускается ручное вмешательство администратора, если автоматический отзыв внешнего назначения невозможен.

## Участники и права

Первая версия поддерживает две роли: сотрудник и администратор.

| Возможность | Сотрудник | Администратор |
| --- | --- | --- |
| Использовать назначенные проекты и подключать агента | Да | Да |
| Приглашать сотрудников и инициировать отзыв при уходе | Нет | Да |
| Создавать проекты и менять состав репозиториев | Нет | Да |
| Подключать организацию GitHub | Нет | Да |
| Назначать и отзывать доступ к проектам | Нет | Да |
| Читать инструкции проекта | При наличии доступа к проекту | При наличии доступа к проекту |
| Редактировать инструкции проекта | Нет | При наличии доступа к проекту |

Администратор управляет составом любого проекта, но роль не открывает инструкции и код автоматически.
Администратор может явно назначить себе доступ к проекту.
Такое назначение предоставляет инструкции и все репозитории на общих условиях.

Участник получает права чтения кода и отправки изменений во все репозитории проекта.
Назначение не предоставляет управление настройками репозиториев и не отменяет правила защищённых веток.
Отдельный режим «только чтение» не входит в первую версию.

Сотрудник может участвовать в нескольких проектах.
Один репозиторий может входить в несколько проектов.
Доступ к общему репозиторию сохраняется, пока его предоставляет хотя бы один разрешённый проект.
Такой доступ сам по себе не открывает инструкции других проектов.

Агент действует в пределах прав подключившего его сотрудника.
Отдельное назначение доступа агенту не требуется и не расширяет права сотрудника.

## Обязательные сценарии

### 1. Приглашение сотрудника

Администратор задаёт адрес приглашения.
Сотрудник принимает приглашение и подтверждает принадлежность своего аккаунта GitHub до получения доступа к репозиториям.
Введённого имени GitHub без подтверждения недостаточно.
Самостоятельная регистрация без приглашения не входит в первую версию.

### 2. Подключение GitHub и создание проекта

Администратор подключает одну организацию GitHub и выбирает её существующие приватные репозитории для проектов.
Один проект может объединять репозитории нескольких сервисов.
Платформа разрешает добавлять только приватные репозитории.
Создание репозиториев, публичные и личные репозитории, а также несколько организаций не входят в первую версию.

В приложении должен быть отдельный модуль интеграций.
GitHub становится первой интеграцией; подключение других сервисов откладывается.
Конкретные технические границы модулей определяет команда.

### 3. Подготовка инструкций

Платформа хранит один редактируемый документ с актуальными инструкциями на проект.
Документ содержит требования к окружению, шаги подготовки и проверочную команду.
Редактировать его может администратор, которому назначен доступ к проекту.

Инструкции описывают способы получения секретов, но не содержат их значений.
История версий, согласование изменений и наследование инструкций откладываются.

### 4. Назначение доступа

Администратор назначает сотруднику доступ к проекту целиком.
Платформа предоставляет инструкции и выдаёт права во все репозитории проекта через GitHub.

Если выдача завершена не для всех репозиториев, платформа показывает неполный доступ.
Она не представляет частичный результат как завершённое подключение.
Сбой GitHub не должен предоставлять сотруднику или агенту данные запрещённых проектов.

### 5. Работа агента и подготовка окружения

Команда выбирает одного поддерживаемого агента разработчика.
Сотрудник подключает этого агента к платформе и выбирает доступный проект для подготовки окружения.
Агент получает только доступные сотруднику проекты, репозитории и инструкции.
Те же ограничения действуют при собственных обращениях сотрудника к платформе.

Агент работает на машине сотрудника в заранее согласованном окружении.
Он выполняет подготовку по инструкциям, проверяет доступ к репозиториям и запускает проверочную команду.
Успешный результат этой команды завершает подключение к проекту.
Если подготовка или проверка не удалась, агент сообщает причину и не объявляет окружение готовым.

Агент может остановиться для действия сотрудника, например входа во внешний сервис или получения секрета у ответственного.
Он объясняет нужное действие и продолжает после подтверждения сотрудника.
Платформа не хранит секреты проектов в первой версии.

### 6. Изменение проекта и его участников

При добавлении репозитория платформа выдаёт доступ всем участникам проекта.
До завершения выдачи она показывает неполный доступ соответствующих участников.

При удалении репозитория платформа отзывает назначения, созданные через этот проект.
Она сохраняет доступ, если его предоставляет другой разрешённый проект.

При исключении сотрудника из проекта платформа закрывает ему и его агенту доступ к инструкциям этого проекта.
Она отзывает назначения на репозитории через этот проект, сохраняя доступ через другие разрешённые проекты.

Отмена назначения через проект и полный отзыв при уходе сотрудника имеют разные границы.
При уходе учитываются также внешние назначения к репозиториям проектов.

### 7. Уход сотрудника

Администратор инициирует отзыв доступа сотрудника ко всем проектам.
Платформа сразу блокирует доступ сотрудника и его агента к платформе, независимо от доступности GitHub.
Уже подключённый агент больше не должен получать новые данные компании через платформу.

Платформа отзывает собственные назначения в GitHub и проверяет фактический доступ к репозиториям проектов.
Проверка учитывает внешние назначения, например доступ через команду GitHub.
Область проверки — репозитории проектов платформы, а не все внешние сервисы компании.

Если внешнее назначение нельзя отозвать автоматически, платформа показывает администратору препятствие.
Администратор устраняет его, после чего платформа повторно проверяет доступ.
До подтверждения отсутствия доступа отзыв остаётся незавершённым.
Если платформа не может проверить результат, она также не объявляет отзыв завершённым.

Если репозиторий проекта стал публичным, платформа показывает это как препятствие и не подтверждает полный отзыв.
Удаление назначений не закрывает публичный доступ к чтению.

При недоступности GitHub платформа сохраняет незавершённое состояние, показывает причину и позволяет повторить операцию.
Успешно закрытые доступы обратно не открываются.

Отзыв прекращает получение новых данных и дальнейший доступ к репозиториям.
Он не удаляет ранее скачанный код, сохранённые инструкции или другие локальные копии.

## Критерии приёмки

| Проверка | Ожидаемый результат |
| --- | --- |
| Полный цикл на настоящем проекте с несколькими репозиториями | Приглашение, подтверждение GitHub, выдача доступа, подготовка окружения и проверенный отзыв проходят последовательно |
| Запрос сотрудника и его агента к неназначенному проекту | Платформа не выдаёт проект, его инструкции или перечень его репозиториев |
| Сотрудник знает имя чужого проекта или репозитория | Знание имени не расширяет права в платформе |
| Администратор не назначил себе доступ к проекту | Он управляет составом проекта, но не получает инструкции или права на код через платформу |
| Администратор явно назначает себе доступ | Он получает инструкции и все репозитории на общих условиях |
| Репозиторий добавлен в проект | Все участники получают права; незавершённую выдачу платформа показывает явно |
| Репозиторий исключён из проекта | Назначения через этот проект отозваны; доступ через другой разрешённый проект сохранён |
| Сотрудник исключён из одного из двух проектов с общим репозиторием | Инструкции исключённого проекта недоступны, общий репозиторий остаётся доступным через второй проект |
| Проверочная команда завершилась ошибкой | Агент сообщает причину и не объявляет окружение готовым |
| Подготовка требует действия сотрудника | Агент объясняет действие и продолжает после подтверждения |
| Сотрудник уходит, пока GitHub недоступен | Платформа сразу блокирует сотрудника и подключённого агента; отзыв в GitHub остаётся незавершённым |
| Внешнее назначение сохраняет доступ к репозиторию | Платформа не объявляет отзыв завершённым и показывает препятствие |
| Администратор пытается добавить публичный репозиторий | Платформа отклоняет добавление; первая версия принимает только приватные репозитории |
| Репозиторий проекта стал публичным | Платформа показывает препятствие и не подтверждает полный отзыв |
| Администратор устранил внешнее назначение | Повторная проверка подтверждает отсутствие доступа перед завершением отзыва |
| Повтор операции после частичного отзыва | Уже закрытые доступы не открываются; оставшиеся доступы отзываются и проверяются |

Перед приёмкой команда фиксирует выбранного агента, поддерживаемое локальное окружение и проверочную команду настоящего проекта.
Критерии описывают ожидаемое поведение; этот документ не подтверждает наличие реализации или пройденных проверок.

## Отложенные возможности

- Несколько компаний, самостоятельная регистрация компаний и несколько организаций GitHub.
- Создание репозиториев и работа с публичными или личными репозиториями GitHub.
- Команды сотрудников, сложные роли и отдельные права «только чтение».
- Каталог общих скиллов и инструментов компании, контроль расходов на модели.
- Агент компании для онбординга, ответов по документации и подбора задач.
- Интеграции с трекерами задач и хранилищами документации, собственный трекер.
- Назначение задач агентам, облачные запуски, несколько параллельных агентов и песочницы.
- Автоматизация проверки изменений, оценки агентов, релизов и сопровождения сервисов.
- Сбор обратной связи для улучшения агентов и расширенные средства наблюдения и восстановления.
- Поддержка нескольких агентов разработчика и универсальная поддержка операционных систем.
- Хранение секретов проектов.
- История версий, согласование изменений и наследование инструкций.

Обработка ошибок выдачи и отзыва доступа остаётся обязательной частью первой версии.
Отложенные средства наблюдения и восстановления не отменяют эту обязанность.

## Решения команды перед реализацией

Заказчик оставил команде интерфейс, способ подключения агента и технические решения.
В рамках согласованного объёма команда определяет:

- Поддерживаемого агента и локальное окружение для проверки полного цикла.
- Интерфейс администратора и сотрудника, способ подключения и идентификации агента.
- Способ входа, подтверждения приглашения и принадлежности аккаунта GitHub.
- Способ создания первого администратора, сроки приглашений и обработку повторных приглашений.
- Способ интеграции с GitHub, необходимые полномочия и проверку внешних назначений.
- Механизм выдачи и отзыва прав с учётом общих репозиториев.
- Технические состояния операций, повторные попытки и способ показа причин ошибок.
- Формат инструкций и способ представления результата подготовки окружения.
- Стек, хранение данных и границы частей приложения, включая отдельный модуль интеграций.

Запрет на хранение секретов проектов не исключает технические учётные данные для работы самой интеграции.
Способ работы с этими учётными данными определяет команда.

Эти решения не могут ослаблять общие ограничения доступа, проверку фактического отзыва или критерии готовности окружения.
Если выбранный способ интеграции не обеспечивает требования, команда возвращает вопрос на согласование до реализации.
