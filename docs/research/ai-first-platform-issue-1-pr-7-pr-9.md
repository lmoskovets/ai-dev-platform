### Роль Issue #1

[Issue #1][map] — карта решений о продукте, а не задача реализации приложения.
Она задаёт развитие вокруг готовых агентов: сначала разработчики, затем возможные сценарии других сотрудников.
Создание собственного coding agent не согласовано; облачные и встроенные сценарии остаются гипотезами.
Основная мотивация — организация AI-first процесса; выигрыш скорости разработки пока не подтверждён.

Карта связывает решения с дочерними вопросами: границы поставки закрывает Issue #2, предметную модель — Issue #8.
Другие вопросы сохраняются открытыми, даже когда соседнее решение уже опубликовано.
Рекомендации агента становятся решениями только после ответа владельца.
Для локального проекта полезен этот порядок фиксации решений; он не требует пересмотра уже согласованной v1.

## Решения, основания и применимость

### 1. Граница продукта: сведения сначала, GitHub-права потом

**Решение источника.** До PR #7 README включал отзыв доступа к репозиториям в первую версию.
PR #7 заменил это обязательство прекращением выдачи сведений через платформу.
Основная поставка предполагает, что сотрудник уже имеет GitHub-доступ.
Даже дополнительный этап обещает отзыв выданных платформой прав, а не проверку всех внешних оснований доступа.

**Почему.** Issue #1 разрешает пересмотреть исходный бриф ради организации AI-first работы вокруг готовых агентов.
Итог Issue #2 фиксирует согласование после сравнения брифа, материала первой версии, карты главы и исследований.
Документ прямо связывает разделение с материалом, где GitHub-доступы вынесены в «дополнительную практику».
Это подтверждённое основание выбора поставки; количественное снижение стоимости или сложности источники не доказывают.

**Доказательства:** [исходный README][before-readme], [итог Issue #2][scope-decision], [новая граница][scope-core], [основания в документе][scope-reasons].

**Локально — отклонить сокращение объёма.** [Выбранная граница v1](../first-version.md#выбранная-граница) требует настоящей выдачи и проверенного отзыва GitHub-доступов.
Отзыв должен учитывать внешние назначения, частичный результат и изменение приватности репозитория.
Учебное разделение этапов внешнего проекта не является решением локального владельца.

### 2. Один владелец разрешений; содержимое принадлежит проектам

**Решение источника.** Модуль «Доступ» владеет участием в проектах, административными полномочиями и правилами разрешений.
Модуль «Проекты» хранит состав проектов и предоставляет содержимое после проверки разрешения.
«Сотрудники» владеет активностью учётной записи; «Подключения агентов» — действительностью подключения и его владельцем.
«Доступ» учитывает эти факты, но не становится их вторым владельцем.

**Почему.** ADR прямо объясняет централизацию: правила человека и агента должны оставаться едиными.
Отклонён вариант распределить участие, административные полномочия и проверку между несколькими владельцами.
Цена решения также названа: сценарии должны взаимодействовать с модулем «Доступ» при назначениях и проверках.

**Доказательство:** [ADR-0001, варианты и последствия][access-adr].
Это распределение ответственности, а не выбор отдельных сервисов, транспорта или механизма хранения.

**Локально — принять принцип сейчас; адаптировать границы модулей.** Принцип соответствует одинаковым ограничениям сотрудника и агента.
Точное разделение остаётся предложением команды, поскольку [локальная v1](../first-version.md#решения-команды-перед-реализацией) пока его не утверждает.
Предлагаемая адаптация:

| Модуль | Ответственность для локальной v1 |
| --- | --- |
| Сотрудники | Приглашение, вход, подтверждение личности, активность учётной записи. |
| Проекты | Состав репозиториев, редактируемый документ инструкций, выдача разрешённого содержимого. |
| Доступ | Назначения проектов, административные полномочия, решения о допустимых действиях и сведениях. |
| Подключения агентов | Владелец подключения, проверка действительности, отзыв подключения. |
| Интеграции | Подтверждённая связь с GitHub, внешние операции, проверка фактических прав и причины препятствий. |

Пятый модуль нужен сразу: [локальный сценарий подключения GitHub](../first-version.md#2-подключение-github-и-создание-проекта) делает интеграцию обязательной.
Модуль «Доступ» определяет основание; «Проекты» определяет репозитории; «Интеграции» выполняет внешние действия.
Такую последовательность ответственности задаёт и [внешняя модель][modules], но она не определяет владельца полного сквозного процесса.
Локально ещё нужно назначить владельца состояния выдачи, повторов и проверенного завершения отзыва.
Это рекомендация исследования, а не найденное решение PR #9.

### 3. Управление проектом не открывает его содержимое

**Решение источника.** Администратор управляет проектами, но читает рабочие сведения только через участие в соответствующем проекте.
Он может явно добавить себя в участники.
Общий репозиторий не раскрывает другие проекты и их инструкции.
Исключение из одного проекта сохраняет участие в остальных.

**Основание.** Эти правила прямо подтверждены моделью; отдельный мотив для каждого ограничения не записан.
Вывод исследования: они разделяют административные действия и доступ к рабочим сведениям.
Такое разделение не является абсолютным запретом администратору получить доступ: источник допускает явное самоназначение.

**Доказательства:** [управление, проекты и участие][membership].

**Локально — принять как уже согласованные ограничения.** [Участники и права](../first-version.md#участники-и-права) устанавливают те же границы.
При переносе нужно сохранить фактический GitHub-доступ к общему репозиторию, пока действует хотя бы одно разрешённое назначение проекта.
Внешняя модель описывает преимущественно видимость сведений и сама эту внешнюю операцию не реализует.

### 4. Подключение агента — отдельный объект, но не отдельный субъект проектных прав

**Решение источника.** Подключение принадлежит одному сотруднику; сотрудник может иметь несколько независимо отзываемых подключений.
Подключение отличается от клиента, запуска и разговора агента.
Оно не получает собственных назначений проектов.
Сотрудник создаёт подключения от своего имени; администратор может отозвать чужое подключение, но не создать его за сотрудника.

**Основание.** Модель приводит пример нескольких компьютеров и явно требует независимого отзыва.
Общий принцип ADR сохраняет единые правила получения сведений.
При этом административная роль сотрудника не означает автоматического делегирования агенту всех управляющих действий.
Допустимые действия агента и дополнительные ограничения подключения оставлены открытыми.

**Доказательства:** [подключения][connections], [ограничения административных действий][agent-authority].

**Локально — адаптировать.** Отдельное отзываемое подключение подходит для блокировки уже подключённого агента при уходе сотрудника.
Несколько подключений одного клиента не означают поддержку нескольких видов агентов.
Количество подключений и управляющие действия агента требуют местного решения; [локальная v1](../first-version.md#5-работа-агента-и-подготовка-окружения) их не фиксирует.
Передача содержимого должна учитывать текущие права сотрудника, а не права на момент создания подключения.

### 5. Отзыв: блокировка платформы отделена от завершения остальных действий

**Решение источника.** Уход делает учётную запись неактивной, прекращает участие в проектах и отзывает подключения.
Неактивность сама запрещает дальнейшую выдачу сведений, даже если другие действия отзыва ещё не завершены.
Возвращение требует явного восстановления, новых назначений проектов и новых подключений.
Ранее скачанный код и сведения не удаляются с машины сотрудника.

**Основание.** Модель прямо запрещает старым приглашениям и подключениям самостоятельно возвращать доступ.
Вывод исследования: блокировка учётной записи обеспечивает общий запрет при частичном выполнении остальных операций.
Технический порядок операций, гарантии для начатых запросов и сроки отзыва источники оставляют открытыми.

**Доказательства:** [уход и возвращение][return], [сквозные сценарии][interactions], [открытые вопросы][open-model].

**Локально — принять немедленную блокировку; адаптировать завершение отзыва.** Это уже требуется [сценарием ухода](../first-version.md#7-уход-сотрудника).
Локальный процесс завершается только после проверки отсутствия фактического доступа к репозиториям проектов.
Недоступный GitHub, внешняя команда или публичный репозиторий оставляют отзыв незавершённым.
Правила возвращения сотрудника стоит согласовать отдельно; внешний PR не добавляет их автоматически в местную v1.

### 6. Инструкции в Git: полезная граница, но другой локальный продукт

**Решение источника.** PR #7 разрешает оставлять инструкции в Git без дублирования в платформе.
PR #9 различает общие инструкции проекта, локальные инструкции репозитория и ссылки на их источники.
Администратор управляет ссылками; авторы репозитория меняют содержимое через Git.
Источник в Git должен находиться в репозитории соответствующего проекта.
Ссылка не предоставляет права чтения; способ получения содержимого пока не выбран.

**Почему.** Итог Issue #2 прямо сохраняет подготовку окружения за сотрудником и его агентом.
Платформа не должна дублировать контекст и управлять окружениями.
Модель допускает выдачу остальных разрешённых сведений при недоступности одной инструкции, но требует явно обозначить неполноту.
Такой результат не означает готовность проекта к работе.

**Доказательства:** [граница ответственности PR #7][scope-responsibility], [инструкции PR #9][instructions].

**Локально — отклонить замену документа набором ссылок.** [Подготовка инструкций](../first-version.md#3-подготовка-инструкций) требует одного редактируемого документа в платформе.
Редактировать его может администратор с назначенным доступом к проекту.
Git-источники и отдельные сущности инструкций репозитория можно отложить до пересмотра этого требования.
Сейчас полезен принцип честного неполного результата: ошибка получения инструкции не означает успешную подготовку.
Локальный критерий строже: подключение завершает успешная проверочная команда, а не доступность сведений или возможность продолжить работу.

### 7. Приглашения и последний администратор: кандидаты на уточнение

**Решение источника.** До принятия существует приглашение, а не учётная запись сотрудника.
Приглашение одноразовое, адресное, отменяемое и ограниченное сроком.
Оно содержит намеченные проекты; при принятии проверяются актуальные назначения и существование проектов.
Если проекты исчезли, сотрудник может принять приглашение без участия в проектах.
Последнего активного администратора нельзя отключить или лишить полномочий до передачи управления другому активному сотруднику.

**Основание.** Источник фиксирует правила, но не публикует подробные альтернативы и аргументацию интервью.
Вывод исследования: правила предотвращают преждевременную выдачу прав, дублирование учётных записей и потерю управления платформой.

**Доказательства:** [приглашения и управление][invitations].

**Локально — адаптировать после уточнения.** Срок, повторное приглашение и первый администратор уже перечислены среди [открытых решений команды](../first-version.md#решения-команды-перед-реализацией).
Намеченные проекты в приглашении — дополнительное удобство, а не обязательное местное требование.
Принятие приглашения не заменяет обязательное подтверждение принадлежности GitHub-аккаунта перед выдачей репозиториев.
Защиту последнего администратора нужно согласовать со сценарием ухода: передача полномочий не должна скрыто отменять обязательный отзыв.

### 8. Документы управляют решениями; протокол и стек остаются открытыми

**Решение источника.** PR #9 оставляет термины в `DOMAIN.md`, а связи и жизненные циклы переносит в отдельную модель.
ADR хранит существенный компромисс владения разрешениями.
`AGENTS.md` начинает направлять агента к согласованному объёму, а не только исходному брифу.
Инструкция чтения отдельно предупреждает: наличие понятия в модели не включает возможность в основную поставку.

**Основание.** Описание PR указывает прежний пробел: агент читал только исходный бриф, без согласованных границ и модели.
Новые указатели связывают планирование и реализацию с принятыми документами.

**Доказательства:** [PR #9][pr9], [AGENTS.md][agent-doc], [порядок чтения доменных документов][domain-pointer].

**Локально — добавить указатель на согласованную v1 сейчас.** В местном `AGENTS.md` правило требований направляет только к исходному брифу.
Документ `docs/first-version.md` уже существует и уточняет этот бриф; его нужно читать перед определением объёма и изменением поведения.
Это рекомендация изменить указатель, а не повторять содержание v1 в постоянно загружаемых инструкциях.

Существующий глоссарий содержит важные местные термины; заменять его внешним нельзя.
После согласования отношений и жизненных циклов их стоит записать в `docs/domain-model.md`.
Если владелец выберет отдельный модуль разрешений, ADR должен сохранить рассмотренные варианты и цену выбора.
Этот отчёт не утверждает модель или ADR и не превращает рекомендации в принятые решения.

**Отложить вместе с локальной v1:** интеграцию задач, общие скиллы, управление процессами, облачные запуски и расширенные роли.
Внешние задачи остаются во внешнем трекере; код, PR, проверки и merge остаются в процессе GitHub.
Такое разделение не требует заранее выбрать схему синхронизации или собственный трекер.
Основания: [направления внешнего проекта][scope-future] и [местные отложенные возможности](../first-version.md#отложенные-возможности).
Упоминание MCP в исторической карте не означает выбранный протокол; это явно подтверждают [документ][scope-reasons] и [Issue #5][issue5].
Внешнее исключение production и deploy также не задаёт местную эксплуатационную политику.

## Что именно уточнил PR #9 после PR #7

PR #9 сохраняет сокращённую поставку PR #7: GitHub-права по-прежнему относятся к дополнительному этапу.
Он превращает общий словарь в модель жизненных циклов, владения данными и проверки разрешений.
«Инструкции могут жить в Git» уточняется правилами принадлежности источников и обработки недоступности.
«Агент действует в правах сотрудника» уточняется самостоятельным отзывом подключения и запретом автоматического делегирования административных действий.

Внутри PR #9 второй [коммит `096caf4`][login-fix] добавляет вход и подтверждение личности в ответственность «Сотрудников».
Он также уточняет, что вход сам не назначает проектные или административные разрешения.
Описание PR называет это исправлением пропуска, найденного при проверке соответствия спецификации.
Это уточнение границы идентификации и разрешений, а не отказ от централизации доступа.

Основной разворот произошёл раньше: PR #7 изменил обязательный GitHub-цикл исходного брифа на дополнительный этап.
В пределах PR #9 обратного разворота нет.

## Полнота проверки и ограничения

- Прочитаны тела и метки Issue #1, #2, #8; проверены все их комментарии с пагинацией.
- Прочитаны описания обоих PR, полные diff, списки коммитов, комментарии, reviews и review threads.
- В Issue #1 и обоих PR комментариев нет. GitHub reviews и review threads обоих PR также пусты.
- В Issue #2 и #8 найдено по одному итоговому комментарию владельца. Оба использованы как источники решений.
- Заявленные Standards/Spec review известны из описания PR и итогового комментария. Публичных текстов этих review нет.
- Проверены файлы на base/head и совпадение деревьев head/merge. Отсутствие новых файлов на ранней базе подтверждается diff и API.
- Прочитаны связанные Issue #3–#6. На дату проверки они открыты и не содержат комментариев.
- GitHub API был доступен. Полного текста живых интервью и названных материалов `content-studio` в изученном репозитории нет.
- Поэтому причины за пределами опубликованных итогов и ADR обозначены как выводы исследования, а не слова владельца.
- Прочитаны местные `AGENTS.md`, инструкции трекера и домена, `DOMAIN.md`, требования и документ v1. Локальных ADR не найдено.

Открыты протокол, клиент, способ чтения Git-источников, подробные полномочия агента и техническое выполнение сквозных операций.
PR #9 также не решает закрытие проектов, удаление последнего репозитория и обработку уже начатых запросов при отзыве.
Источники: [модель открытых вопросов][open-model], [Issue #3][issue3], [Issue #4][issue4], [Issue #5][issue5], [Issue #6][issue6].
Эти PR подтверждают опубликованные проектные решения, но не работоспособность приложения или выполнение локальных критериев приёмки.
